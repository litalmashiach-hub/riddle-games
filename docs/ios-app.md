# The iPhone and iPad app

The app is the same game as the website, wrapped in a native shell with [Capacitor](https://capacitorjs.com) 8.
The shell lives in `apps/mobile`; the Xcode project is `apps/mobile/ios/App/App.xcodeproj`.
The website's own build (`pnpm build` → `apps/web/dist`) and its deploy are not touched by any of this.

## The one place for the app's identity

`apps/mobile/ios/AppIdentity.xcconfig` holds the bundle identifier, the name under the icon, the version and the
build number. Xcode and `capacitor.config.ts` both read it. The version is 1.0, build 1. **The identifier and the
name are placeholders** until the owner picks the final ones. Raise `APP_BUILD` for every upload to App Store Connect.

## The app build of the game

`pnpm build:app` builds the game into `apps/web/dist-app` (`vite build --mode app`). It differs from the website in
three ways, all behind `APP_SHELL` in `apps/web/src/appShell.ts`:

- no service worker is built or registered (the files are already inside the app);
- the address switches `?all` and `?debug` do nothing;
- the home-screen-web-app parts (manifest, launch images, touch icons) are left out.

## Build it on a Mac

Needs Xcode 26 or newer (Capacitor 8's minimum), Node 22 and pnpm.

```sh
pnpm install
pnpm ios:sync        # builds the app content and copies it into the Xcode project
pnpm --filter @riddle/mobile exec cap open ios    # opens Xcode
```

In Xcode choose a simulator and press Run. From the command line, unsigned, for the simulator:

```sh
xcodebuild -project apps/mobile/ios/App/App.xcodeproj -scheme App -configuration Release \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath build/ios CODE_SIGNING_ALLOWED=NO build
```

## The lowest iOS it runs on

The app allows iOS and iPadOS 16.4 and later: `IPHONEOS_DEPLOYMENT_TARGET = 16.4` in all four build settings of
`App.xcodeproj`, which the built app carries as `MinimumOSVersion 16.4`. Below that the game breaks: on iOS 15.0 to
15.3 it never gets past its loading dots (a 3D package calls `Object.hasOwn`, and the style sheet uses cascade
layers), and below 16.2 the gold, green and red buttons lose their fill (Tailwind CSS 4 writes their gradients
`in oklab`). 16.4 is the system Tailwind CSS 4 is built for, and every device that runs iOS 16 can update to it.
`ios/App/CapApp-SPM/Package.swift` says `.iOS(.v16)`: `cap sync` rewrites that line from the major number of the
Xcode project's target alone, so it can't say 16.4, and a Swift package only sets a floor for its own code. The app's
16.4 governs. `apps/mobile/src/shellSettings.test.ts` checks both. Raise them together, in the Xcode project first,
then run `cap sync`.

Run `pnpm ios:sync` again after every change to the game. `apps/mobile/ios/App/App/public` and
`capacitor.config.json` are generated by it and not committed.

A build for a real device or for the store needs signing: the owner's Apple developer team, set in Xcode under
Signing & Capabilities. Nothing in the repository holds a certificate, key or team.

## Build it on the runner

The workflow `.github/workflows/ios.yml` (added in its own pull request) does the same on a hosted macOS runner for
every pull request: builds the app content, syncs Capacitor, builds the app unsigned for the simulator, starts it
in a simulator and uploads screenshots as the run's `ios-simulator-screenshots` artifact. There is no Mac in the
team's workspace, so this run is how a change to the iOS project is proven.

## Upload to TestFlight

`.github/workflows/testflight.yml` builds the store version on a hosted Mac, signs it with the owner's Apple
Distribution certificate and App Store provisioning profile, and uploads it to App Store Connect, where it shows
under TestFlight. It is run by hand (Actions, "TestFlight upload", Run workflow). The owner's own steps, from joining
Apple's program to Submit for Review, are in `docs/launch-steps.md`.

### Why manual signing

Every run gets a new Mac. Automatic signing through an App Store Connect key (`-allowProvisioningUpdates`) makes
Xcode create an Apple Development certificate on each new Mac, whose private key is lost when the Mac is; Apple's
developer forum reports that later runs then fail with "private key is not installed in your keychain". So the
workflow signs by hand, the way GitHub documents for its Macs ("Installing an Apple certificate on macOS runners for
Xcode development"): the owner makes one distribution certificate and one App Store profile, once, adds them as
secrets, and every run imports them into a keychain that exists only for that run. A run creates nothing in the
owner's Apple account. The API key is used only for the upload, so its role can be Developer, the smallest that
Apple lists as able to upload builds.

The owner has no Mac, so `apps/mobile/scripts/make-signing-files.sh` makes the private key and the certificate
request with openssl (in a GitHub codespace, Git Bash on Windows, or Linux), and after Apple has issued the
certificate and profile, checks that they belong together and writes the three secrets as text files. It sends
nothing anywhere. The `.p12` uses PBE-SHA1-3DES, which macOS's `security import` reads whatever openssl made it.

### What it needs

All added by the owner in the repository's settings (Settings, Secrets and variables, Actions); nothing is committed:

| Name | Kind | What it is |
| --- | --- | --- |
| `APP_BUNDLE_ID` | variable | The bundle identifier of the app's record in App Store Connect. Not needed once `AppIdentity.xcconfig` holds the real one. |
| `APPLE_TEAM_ID` | variable (or secret) | The Apple team ID, 10 characters. |
| `APP_STORE_CONNECT_KEY_ID` | secret | The API key's Key ID. |
| `APP_STORE_CONNECT_ISSUER_ID` | secret | The Issuer ID shown above the team's keys. |
| `APP_STORE_CONNECT_KEY` | secret | The whole text of the key's `.p8` file. |
| `APPLE_DISTRIBUTION_CERTIFICATE` | secret | The Apple Distribution certificate with its private key, a `.p12` as base64 text. |
| `APPLE_DISTRIBUTION_CERTIFICATE_PASSWORD` | secret | The `.p12`'s password. |
| `APPSTORE_PROVISIONING_PROFILE` | secret | The App Store profile for the app's identifier and that certificate, as base64 text. |
| `BUILD_NUMBER_OFFSET` | variable, optional | Added to the run number, if builds were ever uploaded some other way with higher numbers. |

Secrets are given to a step only on a run by hand (each is written `github.event_name == 'workflow_dispatch' &&
secrets.X`), so a pull request from a branch of this repository, which GitHub would otherwise give them to, gets
empty values. The actions are pinned to full commit hashes, with the tag beside each.

### What a run does, in order

1. `apps/mobile/scripts/testflight-preflight.sh` checks that each of the above is set and well formed, that the
   bundle identifier is not the `com.example` placeholder, and that the profile is not a development or ad hoc one.
   If not, the run stops there, before anything is built, and lists what to add where. It prints only whether each
   value is set, never a value.
2. Sets the bundle identifier and the build number in the runner's copy of `AppIdentity.xcconfig`. The build
   number is `BUILD_NUMBER_OFFSET + the run number`, so it goes up with every run. Nothing is committed.
3. `pnpm test` and `pnpm ios:sync` with `RELEASE=1`, so the About screen's placeholder check fails the run while the
   contact, publisher or policy date is still empty.
4. `apps/mobile/scripts/testflight-signing.sh` makes a keychain for the run, imports the certificate (and refuses
   one that isn't Apple Distribution, or isn't valid now), and checks the profile: App Store type, the team, the
   app identifier, not expired, and holding the imported certificate. Each refusal says which file to make again.
   It then sets manual signing (`CODE_SIGN_STYLE`, `DEVELOPMENT_TEAM`, `CODE_SIGN_IDENTITY`,
   `PROVISIONING_PROFILE_SPECIFIER`) on the app target's Release configuration only, in the runner's copy of the
   project: given on the command line they would reach the Swift package targets too, which refuse a profile.
5. `xcodebuild archive`, signed; the archive's signature and embedded profile are checked.
6. `xcodebuild -exportArchive` with `method` app-store-connect, `destination` export and manual signing: the `.ipa`.
7. `xcrun altool --upload-app` with the API key: the upload.
8. Removes the key file, the keychain and the profile, whatever happened.

On a pull request that changes the workflow or its scripts, and by hand with "Check mode" ticked, it runs steps 1
to 3, reports what is missing without failing, archives the app unsigned and checks the archive's identifier,
build number and privacy manifest. Then it runs step 4: with the owner's files when they are set (on a run by
hand), else with a throwaway certificate made on the runner by `make-signing-files.sh` itself and a stand-in
profile UUID, and checks the app target's resulting signing settings and that this Xcode's `altool` has the upload
options used. It stops before signing. A pull request never signs or uploads.

What only the owner's first real run can show: that Apple's certificate and profile sign the archive (step 5), and
that Apple accepts the upload (step 7). If a run fails there, its log and the `testflight-export-logs` artifact say
why.

## What the shell sets

- Sideways only, both directions, on iPhone and on iPad (`Info.plist`, and `GameViewController.swift`). The
  iPad side also sets `UIRequiresFullScreen`, which Apple has deprecated since iPadOS 26 (technote TN3192) but
  which is still what lets an iPad app list fewer than four orientations. On iPadOS 26 the key itself no longer
  stops resizing: an iPad held upright shows the game sideways and smaller, with dark bars above and below,
  and a window that is resized keeps its sideways shape. `apps/mobile/src/shellSettings.test.ts` checks these
  settings. Before building with the iOS 27 SDK, read TN3192 again: there the key gives "discrete resizing".
- No status bar; the page keeps clear of the notch and home bar with CSS safe-area insets.
- No page scroll, bounce or pinch zoom of the page (`GameViewController.swift`, `capacitor.config.ts`);
  text selection and long-press menus are already off in the game's CSS.
- Launch screen: `Base.lproj/LaunchScreen.storyboard` showing the `Splash` image on the game's dark blue.
  `GameViewController.swift` keeps the same picture over the web view until the game has drawn its first screen, then fades it
  out, so the launch screen goes straight into the game with no empty frame between.
- Icon: one opaque 1024 pixel PNG. Icon and launch image are rendered from `apps/web/public/icons/icon.svg` and
  `apps/mobile/art/launch.svg` by `apps/mobile/scripts/render-art.mjs`; run it only when the art changes.

## Feeling like an app

Apple refuses apps that feel like a wrapped website. What the game does about it, and where:

- **Safe areas.** The scene fills the screen edge to edge. Everything a player reads or taps keeps clear of the
  notch or Dynamic Island, the rounded corners and the home bar, with `env(safe-area-inset-*)` in the shell's
  styles (`apps/web/src/screens`, `.safe-top` in `index.css`). A sideways list of level cards passes under
  the notch while it is swiped and rests inside the insets at both ends, as a native list does.
- **No web-page gestures.** A long press selects no text and opens no menu, a double tap or pinch does not zoom
  the page, and the page as a whole never scrolls or bounces. Most of that is in `index.css` and
  `pwa/register.ts` for the website too. The app adds, in `apps/web/src/nativeFeel.ts` and under
  `html.app-shell` in `index.css`: no context menu, nothing can be dragged out of the page, the page can't be
  scrolled even by script, and buttons show their pressed look reliably. Long text (a rules card, the About
  screen) still scrolls inside its own box. Text that is meant to be copied carries the class `select-text`
  and keeps its menu.
- **Touch response.** A tap that does something gives a light tick: every button, tab, switch and link of
  every screen, a tap on something in the 3D scene that takes taps, and every move. It is in
  `apps/web/src/haptics.ts` and goes through Capacitor's own plugin, `@capacitor/haptics`
  (`Haptics.impact`, style light, which is UIKit's `UIImpactFeedbackGenerator`). A device without a haptic
  engine, such as an iPad, does nothing. So does the website: its build holds none of this code.
- **Which switch.** The tick follows the game's sound switch. It stands beside the click sound as the game's
  answer to a tap, so one switch quiets both, and nothing new is stored on the device (the privacy policy
  speaks of stars and two settings). A player who wants the sound without the tick has iOS's own switch for
  that: Settings, Sounds & Haptics, System Haptics, which UIKit's feedback generator obeys by itself.

A new screen or level needs to do nothing for the tick or the gestures. For the safe areas, pad anything that
is fixed to an edge with `max(<its normal gap>, env(safe-area-inset-<edge>))`.

`e2e/tests/native-feel.spec.ts` checks all of this in Chromium: the layout against insets that the test sets
(Chromium has no notch of its own), the gestures, that the website gives no touch response, and, against the
app build with a stand-in for the native side of the bridge, that each kind of tap makes exactly one
`Haptics.impact` call. The tick itself can only be felt on a real iPhone.

## The privacy manifest

`apps/mobile/ios/App/App/PrivacyInfo.xcprivacy` is the app's privacy manifest. It is in the Xcode project's
resources, so it is copied to the top of the built `App.app`. It declares:

- no tracking (`NSPrivacyTracking` = false) and no tracking domains;
- no collected data types;
- no "required reason" API.

The last list is empty because it is true, not because it was skipped. Apple names five groups of such APIs:
file timestamps, system boot time, disk space, active keyboards and `UserDefaults`. Apple asks an app to declare
what its own code calls, and an SDK to declare its own calls in its own manifest. The app's three Swift files call
none of them. Capacitor and Cordova 8.6.2 carry their own manifests inside their frameworks, also with nothing
declared, and their sources call none either. The game's stars and settings are kept by the web view's
`localStorage`, which is WebKit's own storage and not a call to `UserDefaults` by the app.

Keep it true. Before adding native code or a Capacitor plugin, check it against Apple's list
(developer.apple.com, "Describing use of required reason API"): a plugin such as Preferences uses `UserDefaults`
and must bring its own manifest, and Swift code of ours that reads `UserDefaults`, a file's dates, free disk space
or the system uptime needs an entry with one of Apple's reason codes here. If the app ever talks to a server or
collects anything, this file and the store's privacy answers change together.

One plugin is installed: `@capacitor/haptics` 8.0.2. Its two Swift files (`Haptics.swift`, `HapticsPlugin.swift`)
call UIKit's feedback generators, AudioToolbox and CoreHaptics and none of the five groups above, it stores and
sends nothing, and it ships no manifest of its own because it has nothing to declare. So the app's manifest is
unchanged by it. `cap sync` writes the plugin into `ios/App/CapApp-SPM/Package.swift`; that file is generated,
and committed so that the Xcode project opens as it is.

## Still open before a store upload

- Final name and bundle identifier, in `AppIdentity.xcconfig`.
- Signing with the owner's Apple developer account: `.github/workflows/testflight.yml` does it once the owner
  has made their certificate and profile and added them, the key and the team (above).
- `Info.plist` declares that the app uses no non-exempt encryption (`ITSAppUsesNonExemptEncryption` = NO). That
  is true of the code today: the game makes no network calls and has no encryption of its own. It is the owner's
  declaration to Apple when a build is uploaded, so the owner should confirm it, and it must be revisited if the
  app ever starts to talk to a server.
- The store's privacy answers in App Store Connect ("Data Not Collected"), to match the privacy manifest. The
  game makes no network calls and stores only progress and two settings on the device.
